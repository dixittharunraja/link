[ ] Auto-update check (BLOCKED ON the installer above — needs a real published installer to check
   against and swap in, not just a dev build)
   - Deliberately MANUAL/opt-in, not silent/forced — settled in discussion: this app is explicitly
     privacy-focused (zero internet dependency for any actual LAN feature — discovery is local UDP
     broadcast, every connection after that is a direct device-to-device TLS socket, no cloud relay
     ever). A background auto-updater phoning home on a schedule cuts against that promise, and a
     user who wants to stay on an older, already-audited build should be able to just do that. So:
     internet is touched ONLY at the moment the user deliberately checks for/fetches an update —
     never in the background, never tied to any core feature working.
   - Desktop: `electron-updater` (same maintainer as electron-builder, drops in cleanly on top of
     the NSIS installer above) with a `generic` HTTP provider pointed at wherever
     rodix/public/installers already serves the installer + SHA256SUMS.txt today — no new hosting
     infrastructure needed. Checks on manual user action (a "Check for Updates" button/menu item),
     shows what's new, user confirms before anything downloads or installs.
   - Android: no true silent auto-update is possible for a side-loaded (non-Play-Store) APK —
     Android has no background self-update mechanism for apps installed outside a store. The
     realistic version: check a version endpoint, download the new APK if the user confirms, then
     hand off to Android's own install-package flow (needs the REQUEST_INSTALL_PACKAGES
     permission), which still requires the user to tap through the system install prompt manually.
     An in-app nudge that saves a trip to the website, not a real "auto" update.

- [ ] File system weight reduction: Build a tailored, lightweight FUSE mounting helper (or cgofuse custom Go bridge) to replace the ~50MB rclone dependency with a minimal native bridge.
      ADDED REQUIREMENT (found this session): fix the write-progress "fake instant completion"
      glitch that rclone's `--vfs-cache-mode full` causes — every write goes to the PC's own local
      disk cache first (near-instant, hence Explorer showing impossible >1GB/s "completed" almost
      immediately), then the actual upload to the phone happens later as a separate, invisible
      background operation (rclone's `--vfs-write-back` delay). The file DOES eventually arrive
      correctly (confirmed — not data loss), but Explorer's progress/speed during the copy is
      pure fiction, and checking the phone (or reloading the mount) before the real background
      upload finishes looks exactly like the file vanished. Root cause is architectural, not a
      one-flag fix: rclone's cache mode is global, not per-operation, so there's no way to keep
      fast cached reads (the whole reason `full` mode was chosen — a lighter mode caused repeated
      real re-GETs when Explorer/media apps probe file metadata) while also making writes honest
      about real transfer speed. A custom mount implementation can fix this properly by only
      caching READS locally and always passing WRITES straight through to the live WSS connection
      synchronously — something rclone's own VFS layer doesn't let us configure separately.
